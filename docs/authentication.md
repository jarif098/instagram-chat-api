# Authentication & Session Management Guide

## 1. Authentication Architecture

Instagram's Web authentication is stateful and cookie-based. Successful authentication results in an encrypted session identifier (`sessionid`) and accompanying security tokens managed by Meta's edge servers.

Direct programmatic login using username and password via HTTP POST without a browser is heavily guarded by Meta's bot-detection systems (reCAPTCHA v2/Enterprise, device integrity checks, dynamic cryptographic challenge scripts, and IP reputation scoring). Attempts to authenticate purely with raw username/password POST requests to `/api/v1/web/accounts/login/ajax/` typically trigger immediate checkpoint challenges (`checkpoint_required`) or 400 bad request blocks unless originating from an established browser session.

### Recommended & Supported Authentication Strategy
1. **Zero-Automation Runtime:** In production, `instachat-api` runs with **zero browser automation dependencies**. It loads an authorized, serialized session file (`session.json`) containing the session cookies.
2. **Interactive Session Extraction (Research Tool):** For initial session setup, a separate development tool (`research/session-extractor.js`) using Puppeteer is provided. It launches an interactive browser where the developer can log in manually, complete 2FA or SMS challenges, and securely export the authenticated session cookies into `session.json`.
3. **Manual Cookie Import:** Developers can also extract cookies directly from their everyday web browser's Developer Tools (Application -> Cookies -> `instagram.com`) and import them into `session.json` or pass them directly as a configuration object.

## 2. Session Cookies & Fields

A valid Instagram Web session comprises the following keys:

| Cookie Name | Required | Purpose |
|---|---|---|
| `sessionid` | **Yes** | Primary encrypted authentication session token issued by Meta. |
| `csrftoken` | **Yes** | Cross-Site Request Forgery prevention token. Must be echoed in the `x-csrftoken` HTTP request header and `_csrftoken` form parameter. |
| `ds_user_id` | **Yes** | Numeric User ID (PK) of the authenticated Instagram user account. |
| `mid` | Recommended | Machine ID tracking cookie generated by Meta. |
| `ig_did` | Recommended | Device ID generated by Meta for browser fingerprinting. |
| `rur` | Recommended | Routing token (e.g. `"PRN\0547433..."`) directing requests to the proper Meta datacenter cluster. |

## 3. Session Storage Format

The library stores and parses session data using a standardized, secure JSON structure:

```json
{
  "userId": "1234567890",
  "username": "example_user",
  "cookies": {
    "sessionid": "REDACTED_SESSION_ID",
    "csrftoken": "REDACTED_CSRF_TOKEN",
    "ds_user_id": "1234567890",
    "mid": "REDACTED_MID",
    "ig_did": "REDACTED_IG_DID",
    "rur": "PRN"
  },
  "cookieString": "sessionid=REDACTED; csrftoken=REDACTED; ds_user_id=1234567890; mid=REDACTED; ig_did=REDACTED; rur=PRN",
  "createdAt": "2026-10-22T00:00:00.000Z",
  "expiresAt": null
}
```

> [!CAUTION]
> The `session.json` file contains live credentials. It must **never** be checked into version control (git), shared in logs, or exposed to unauthorized parties. The `.gitignore` file is pre-configured to exclude all `session*.json` files.

## 4. Session Validation & Health Check

Before initiating messaging operations, the library verifies whether the current session is alive:

1. **Health Check Request:** Performs a lightweight `GET` request to `https://www.instagram.com/api/v1/direct_v2/inbox/?limit=1`.
2. **Response Evaluation:**
   - **HTTP 200 OK with `"status": "ok"`:** The session is active and healthy. The client transitions to the `ready` state.
   - **HTTP 401 Unauthorized or Redirect to `/accounts/login/`:** The session has expired or been revoked. Emits an `auth_error` event and throws `AuthenticationError`.
   - **HTTP 400 with `checkpoint_required`:** Meta has flagged the account for a verification checkpoint (e.g., SMS, email, selfie verification). Emits `auth_error` with `checkpoint_required` diagnostics.
   - **HTTP 429 Too Many Requests:** The client has hit rate limits. Emits `rate_limit` event and invokes backoff logic.

## 5. Security & Redaction Rules

1. **Logs:** All internal loggers (`src/utils/logger.js`) run structured masking algorithms that automatically scrub cookies, tokens, and authorization headers before outputting to stdout or files.
2. **Crash Dumps:** Any network exceptions caught by the transport layer sanitize request configurations to strip the `Cookie` and `x-csrftoken` headers from the error message and call stacks.
3. **No Credential Storage:** The library never prompts for or stores cleartext account passwords in code or configuration files.
